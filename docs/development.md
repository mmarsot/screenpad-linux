# Development

## Layout

| Path | What it is |
|---|---|
| `screenpad.py`, `screenpad_display/` | the display CLI, installed as `/usr/local/sbin/screenpad` |
| `touchbar.py`, `screenpad_touchbar/` | the touch bar daemon and CLI, installed as `/usr/local/bin/screenpad-touchbar` |
| `screenpad_app/` | the [client library](app-api.md#the-python-client-library) for touch bar apps, installed next to the programs and pip-installable on its own |
| `gnome-shell/screenpad-touchbar@screenpad/` | the GNOME Shell extension that draws the bar and the pages below it: `extension.js`, `tiles.js`, `pages.js`, `notifications.js`, `safeguard.js`, `keepout.js` (keeping the pointer, windows and the overview off the ScreenPad) and `osd.js` (Fn+F6's ScreenPad on indicator) use GNOME Shell; `contract.js`, `scene.js`, `widgets.js`, `cards.js`, `feedback.js`, `repaint.js`, `fence.js` and `fnkey.js` are plain modules with its logic, which the tests run under node; `click.wav` is the press click |
| `gnome-shell/make_click.py` | writes the extension's `click.wav` (`python3 gnome-shell/make_click.py`); not installed |
| `systemd/` | the boot unit, the resume hook, and the touch bar's user unit |
| `udev/` | the `/dev/uinput` access rule, and the ScreenPad backlight rule that lets group `input` run `screenpad light` and `dark` |
| `initramfs/` | the initramfs hook, used only when nvidia-drm is in the initramfs |
| `install.sh` | installs, uninstalls and purges (run as root) |
| `tests/` | unit tests; `touchbar-v1-default.toml` to `touchbar-v5-default.toml` are configs earlier versions wrote, for the migration tests |
| `docs/` | this documentation; `docs/images/` holds the screenshots, `docs/assets/` the README's banner (see [its README](assets/README.md)) |
| `AGENTS.md`, `.agents/skills/` | the guide for contributors and coding agents: an index and one skill per area (`.claude/skills` links to it; `CLAUDE.md` imports `AGENTS.md`) |
| `Makefile`, `pyproject.toml`, `uv.lock`, `package.json`, `package-lock.json`, `eslint.config.js`, `.prettierrc.json` | the development checks and their pinned tools; nothing here is installed. `pyproject.toml` also makes the repository, built as a package, the client library `screenpad_app` alone (pip only; uv never builds it) |
| `.github/workflows/ci.yml` | CI: the same checks on every pull request |
| `.no-mistakes.yaml` | the commands the no-mistakes review pipeline runs |

The programs are Python 3 (3.11 or newer, standard library only) and run from the checkout: `./screenpad.py status`, `./touchbar.py check`. `screenpad.py` and `touchbar.py` are small launchers: run in isolated mode (`python3 -I`), they put the directory they really live in on `sys.path` and call `main()` in their package, `screenpad_display` or `screenpad_touchbar`. `install.sh` copies them with their packages, and the client library `screenpad_app`, to `/usr/local/lib/screenpad/` and links `/usr/local/sbin/screenpad` and `/usr/local/bin/screenpad-touchbar` to them, so the checkout and the installed copy have the same layout. `screenpad_app` imports nothing of the daemon: apps use it from their own repositories, as the agent app, [screenpad-agents](https://github.com/mmarsot/screenpad-agents), does.

Each package has one module per concern, each under about 500 lines:

| Module | What it holds |
|---|---|

| `screenpad_display/grub.py` | `grub show|apply|remove` |

| `screenpad_touchbar/keys.py` | key names and combos, the key device's presses |

| `screenpad_touchbar/config.py` | `touchbar.toml`: the bar's spots, the bar's and the apps page's items, `[notifications]`, `[screensaver]` and `[pager]`, parsing and loading |

| `screenpad_touchbar/config_edit.py` | editing the config in place: the height, adding, moving and removing apps among the items, and moving an item's block between `[[bar]]` and `[[apps]]` |

| `screenpad_touchbar/migrate.py` | bringing an earlier config up to date: its default, its default blocks, its buttons and shortcuts turned into items |
| `screenpad_touchbar/scene.py` | the tiles in `touchbar.json` |
| `screenpad_touchbar/splitter.py` | the zone split between the bar, the apps surface and the virtual touchpad, and handing an apps page touch to the virtual touchpad |
| `screenpad_touchbar/decide.py` | the apps page's touches: which move the pointer, which tap or press what is under them |
| `screenpad_touchbar/pager.py` | the two pages: the swipe along the bar, the page button, the return to the touchpad |
| `screenpad_touchbar/widgets.py` | apps' pages for the apps page: validating a page and its widgets |
| `screenpad_touchbar/surface.py` | the apps page: the home page's list (its items, then the apps' pages), an app's page laid out below the bar, and what touches on its widgets do |
| `screenpad_touchbar/bar.py` | what touches on the items, the grip and a question do, and what an item does from the apps page |
| `screenpad_touchbar/protocol.py` | validating app messages, questions as apps send them |
| `screenpad_touchbar/notify.py` | GNOME notifications: normalizing, the mirror rules, the question one becomes |

The imports between them go one way (no cycles): `common` and `codes` import nothing of the package, and `cli` sits on top.

## Checks

```sh
make check
```

runs, in order, everything CI runs; each step is also a target of its own:

| Command | What it checks | Tools |
|---|---|---|
| `make format-check` | formatting; `make format` applies it | ruff format (Python), Prettier (the extension's JavaScript) |
| `make lint` | likely mistakes | ruff check, ESLint |
| `make typecheck` | types | mypy, with `check_untyped_defs`, on the programs and the tests |
| `make test` | the unit tests below | `python3 -m unittest`, standard library only |

The Python tools run through [uv](https://docs.astral.sh/uv/) (versions pinned in `pyproject.toml` and `uv.lock`), the JavaScript ones through npm (`package.json`, `package-lock.json`; `make` runs `npm ci` the first time). Only `make test` works without them; it uses node, when installed, for the extension's tests. CI (`.github/workflows/ci.yml`) runs the format check, lint and typecheck once and the tests on Python 3.11 and 3.14, with node, on pull requests only (a push to a pull request's branch runs it once, as the pull request; nothing runs on a push alone), each job stopped after 10 minutes so a hang fails instead of sitting in progress.

Changes go through the [no-mistakes](https://github.com/kunchenguid/no-mistakes) review pipeline before they reach GitHub; the rules for contributors and agents are in [AGENTS.md](../AGENTS.md) and its skills.

## Tests

```sh
make test   # or: python3 -m unittest discover -s tests
```

They need no root and no hardware. There is one file per area: `tests/test_screenpad.py`, `test_screenpad_panel.py` and `test_screenpad_grub.py` cover the display CLI, `test_install.py` `install.sh`, `test_touchbar_config.py`, `test_touchbar_bar.py`, `test_touchbar_scene.py`, `test_touchbar_apps.py`, `test_touchbar_cards.py`, `test_touchbar_clicks.py`, `test_touchbar_notify.py`, `test_touchbar_pager.py`, `test_touchbar_surface.py`, `test_touchbar_decide.py`, `test_touchbar_commands.py`, `test_touchbar_fnkey.py`, `test_touchbar_extension.py`, `test_touchbar_extension_cards.py`, `test_touchbar_extension_widgets.py`, `test_touchbar_extension_repaint.py`, `test_touchbar_extension_keepout.py` and `test_touchbar_extension_fnkey.py` the touch bar, `test_app_protocol.py` and `test_app_client.py` the app protocol's version and the client library, and `tests/test_skills.py` the skills (their front matter, the index in `AGENTS.md`, the `.claude/skills` link, and that their links and repository paths resolve). `screenpad_support.py`, `touchbar_support.py` and `app_support.py` hold what each program's tests share. The display tests build a fake sysfs/debugfs/procfs/`/etc` tree in a temporary directory and replace the i2c reads and `update-grub`. They cover:

- checksum fixing: a synthetic EDID with a wrong CTA checksum, and the known single-byte `0x3e` → `0x6f` case;
- DMI refusal;
- card/connector/i2c/debugfs discovery, including swapped card numbers and debugfs directories named by minor;
- the exact writes `on`, `off` and `replug` make, on unlocked and locked-down kernels;
- `dark` and `light` from all four starting states, leaving the connector and the active flag alone and needing no root, `light` refused while the ScreenPad is off, a refused backlight write naming the udev rule, and `replug --keep-dark` keeping a darkened panel dark (and relighting a lit one);
- the panel, through a fake asus-wmi (its `update_screenpad_bl_status()` choice, the backlight core's skip of unchanged `bl_power`, and this unit's polarity) plus a fake compositor that enables the forced connector: `on` and `replug` end lit, with `POWER=0` as the last call while the connector is enabled, and `off` ends dark, from all four starting states (`bl_power` 0/4 × firmware reports powered or not);
- lockdown detection, kernel command line parsing, and the kernel's `edid_firmware` connector matching;
- the DDC retry;
- `grub show/apply/remove`, including that apply then remove gives back the original file;
- `install.sh` against a fake root (`DESTDIR`), with stub `id`, `systemctl`, `lsinitramfs`, `update-initramfs` and `udevadm` first on `PATH`, including the touch bar's files, the backlight udev rule and its `udevadm trigger`, the installed resume hook run with a stub `systemd-run` (passing `replug --if-active --keep-dark`), the programs' links and packages in `/usr/local/lib/screenpad/` (an update replacing a single-file install and dropping a module that is gone), none of the agent app any more, and an earlier version's agent app left in place with the exact commands that remove it printed (and removed by uninstall), and the installed commands running in isolated mode, including the extension's fallback command (`CLI_FALLBACK`). These tests are skipped when run as root.

- the client against the daemon's own `AppServer` in a thread (its version range patched for a bar too new or too old): `hello` and its `welcome`, a bar too new, too old and from before the version (and version 1 welcome there), the refusal through `receive()`, other refusals, no daemon and no `XDG_RUNTIME_DIR`, the bar going away; tiles and pages sent only when changed, a page sent again after `unpage` however it was sent, taps, long presses, answers and `cancel` coming back, errors after the welcome, a tile or page another app's; `Link` connecting when due, a hello that cannot be sent retried (its socket closed), a loss logged once and retried, everything shown again after a reconnect, a refusal logged once over retries, no daemon quiet; and the library importing nothing of the daemon.

The screenshots in `docs/images/` were rendered by the extension in a headless GNOME Shell 50.1 (`gnome-shell --headless --virtual-monitor 1920x1080`) fed the scenes the daemon's own code publishes (a script importing `screenpad_touchbar`, with the virtual monitor's identity from `org.gnome.Mutter.DisplayConfig`), then cropped to the bar, or scaled to half for the pages (`touchbar-touchpad-page.png` with the shell's system bus a second `dbus-daemon` in the private runtime directory, given in `DBUS_SYSTEM_BUS_ADDRESS`, where a stand-in UPower display device gives the battery level and changes it with `PropertiesChanged`; the shell then warns in a banner that screen locking needs the GNOME display manager, so turn banners off on the private bus with `org.gnome.desktop.notifications show-banners false`; `touchbar-apps-page.png` and `touchbar-app-page.png` with two `[[apps]]` items and two apps' pages given through the daemon's own `Apps`; `touchbar-move.png` with a drag fed as device frames through the daemon's own `Splitter` and `route`). Run it under `dbus-run-session` with its own `HOME` and `XDG_*` directories, so it touches nothing of your session. Keep `XDG_CURRENT_DESKTOP` as your session has it (`ubuntu:GNOME` on Ubuntu): Ubuntu's schema overrides, which give the icons and font the screenshots show, apply only to that desktop. **Set them, and unset `DBUS_SESSION_BUS_ADDRESS`, `DISPLAY` and `WAYLAND_DISPLAY`, before starting `dbus-run-session`**, not in the script it runs: services the private bus starts on demand (dconf, gvfs, the portals) get the environment `dbus-run-session` started with, so otherwise `gsettings set` and the shell's own settings writes land in your real `~/.config/dconf/user`. Comparing that file's checksum before and after a run shows it stayed untouched; `org.gnome.Shell.Screenshot` answers only some bus names, such as `org.gnome.SettingsDaemon.MediaKeys`, which a script can own on that private bus. Keep the runtime directory's path short: Unix socket paths are limited to 108 bytes. To check notifications there, send them with `org.freedesktop.Notifications.Notify` on that bus; GNOME 50 sends `ActionInvoked` and `NotificationClosed` only to the notification's sender, so subscribe from the connection that sent it rather than with `gdbus monitor`. `docs/images/touchbar-notification.png` (a real notification, mirrored by the extension to the daemon's socket, which the script serves) and `touchbar-ask.png` come from such a session. To check that the screensaver stays behind windows and the apps page covers them, open a window there (`zenity --info` with `WAYLAND_DISPLAY=wayland-0` in the private runtime directory). To check keeping the desktop off the ScreenPad, start the shell with two virtual monitors (`--virtual-monitor 1920x1080 --virtual-monitor 1920x515`), place them with `org.gnome.Mutter.DisplayConfig.ApplyMonitorsConfig` (method 1, temporary) on each side, give the scene the second one's identity, and drive the pointer with a Clutter virtual pointer's relative motion, as the touchpad's, through `org.gnome.Shell.Eval` (it needs `global.context.unsafe_mode`, which a throwaway extension in the private `HOME` can set). Mutter lets a pointer through a barrier only when it sits exactly on the line, which a warp straight onto it can do: start each push away from the edge. To check Fn+F6's ScreenPad on indicator, publish the daemon's scenes round the cycle and call `org.gnome.Shell.ShowOSD` with `{'icon': <'touchpad-disabled-symbolic'>}` as gsd-media-keys does (refused outside unsafe mode, like `Eval`), in both orders, then read the indicator's icon and label from `Main.osdWindowManager._osdWindows` through `Eval`. The private session's extensions go in `$XDG_DATA_HOME/gnome-shell/extensions`, and disabling one there adds it to `org.gnome.shell disabled-extensions`, which the next run must clear.
